The benchmark

Beyond code translation.
Preserving executable behavior.

Migrating PyTorch to JAX is a structural rewrite: stateful modules become pure, compilable functions with explicit parameters and state. T2J-BENCH tests whether that rewrite preserves the original system.

The central challenge

A repository can satisfy its interface and still diverge in forward numerics, gradients, optimizer trajectories, or decode behavior. T2J-BENCH measures those differences by running the code.

Task coverage

One migration contract.
Two sides of the ML lifecycle.

Every task starts with a self-contained PyTorch source repository and raw checkpoint. Agents deliver native JAX/Flax code, a torch-free checkpoint converter, and an executable training or serving path.

Execution-grounded evaluation

Run it. Compare it. Verify independence.

Each candidate runs in a separate, offline verifier with PyTorch removed. Ground truth is recorded from the original PyTorch repository; the reference JAX solution is evaluated as a candidate.

01 / Spec

Is it a genuine migration?

Check structure, public interfaces, and framework independence. Hidden PyTorch dependencies cannot earn equivalence credit.

02 / Numeric

Do the numbers agree?

Compare module outputs, composed forward passes, losses, gradients, and step-wise computations against frozen references.

03 / Behavioral

Does the system behave the same?

Evaluate training dynamics, held-out behavior, and paged decode execution under a uniform runtime budget.

R = sspec × (0.5 snum + 0.5 sbeh)

A spec-gated reward in [0, 1], with continuous, threshold-free numeric and behavioral similarity.

7 evaluation levels

L0–L6 cover independence and structure through end-to-end execution.

3 random seeds

Each configuration is evaluated across all 63 tasks; results are seed averages.

0.980 oracle reward

A known-good JAX solution establishes task solvability and remaining headroom.

TwinHarness

Use the source as
an executable specification.

A reference-grounded diagnose–migrate–verify loop turns the task-visible PyTorch implementation into structured feedback for the next edit.

A strict information boundary

TwinHarness uses the task specification, visible PyTorch source, released checkpoint, and candidate execution. It does not access hidden tests, frozen reference outputs, reference JAX solutions, verifier code, or benchmark rewards.

Structured refinement

Better feedback makes
the next iteration count.

With Claude-Code / opus-5, TwinHarness improves from 0.662 after one round to 0.723 after two. Ordinary continuation improves from 0.649 to 0.658.

With OpenCode, second-round regressions affect 2 of 63 tasks under TwinHarness versus 22 under ordinary continuation. Each method starts from its own first-round candidate.
